# LifeTrack

A personal Android app for tracking calories, activity, habits, a daily routine, screen time and alarms.
Everything lives in one SQLite file on the phone. Nothing is uploaded anywhere, there is no
account, and no network permission is requested.

## Open it in Android Studio

1. Android Studio → **Open** → pick this folder.
2. Let Gradle sync.
3. Plug in your phone (USB debugging on) or start an emulator, then press **Run ▶**.

**Build JDK must be 21.** Gradle 8.11.1 does not support the JDK 25 that recent Android Studio
versions bundle. The project already pins it in `.gradle/config.properties`
(`java.home=…/.jdks/jbr-21.0.11`) and Studio's Gradle JVM is set to `#GRADLE_LOCAL_JAVA_HOME`,
so Studio is fine as-is. From a terminal, export `JAVA_HOME` to that JDK 21 first or the build
fails with a bare `25.0.3`.

Toolchain: AGP 8.9.1, Gradle 8.11.1, Kotlin 2.0.20, compileSdk 36, minSdk 26, targetSdk 34.
`compileSdk 36` is required by `androidx.health.connect:connect-client:1.1.0`.

## Navigation

Three tabs. **Home** is the day summary (calories, activity, habits, routine, screen time,
alarms); **All** is every section as a round button; **Settings** is the only place the app asks
for any access.

| Section | What it does |
| --- | --- |
| **Calories** | Pick the meal you are eating, search 750 foods, log it. Calories, protein, fibre, vitamins. |
| **Activity** | Steps (and when you walked), distance, calories burned, active minutes, heart rate, sleep. |
| **Habits** | Timed habits (stopwatch, milliseconds) and counted habits, with a month calendar. |
| **Routine** | The fixed day, each item scored hit or miss, with streaks and a month of dots. |
| **Alarms** | The daily routine's usual times, plus your own reminders that notify or ring. |
| **Screen time** | Per-app usage and daily limits that actually close the app. |

A section opens on top of the tab you came from, with the bar still showing (All lit), so Back
returns where you were. Home's cards and notification taps open the same sections.

### Settings and first run
`ui/settings/Access.kt` lists every access LifeTrack can use - notifications, exact alarms,
full-screen alarms, unrestricted battery, Health Connect, Health Connect in background, physical
activity, usage access, limit blocking - with what each is for. The Settings tab shows each one
On/Off with **Turn on** (asks, or opens the right system page) or **Manage** (the system page where
it can be switched off; Android never lets an app revoke its own access). Sections never ask
themselves: when something they need is off they show a one-line link to Settings.

A fresh install opens on Settings with a welcome card (`FirstRun`), and nothing requests a
permission on launch. Routes are in
`Nav.kt` (`Sections`); the grid is `ui/all/AllScreen.kt`.

## Things worth knowing

### Calories
- The **meal slot selector** is a control, not a summary. Whichever of Breakfast / Lunch /
  Snacks / Dinner is selected is where new food goes, and it persists across restarts
  (`Settings.activeSlot`).
- Search matches the start of the name *or* the start of any word inside it, so `da` finds
  Daal, Daliya and Dahi, and `pan` finds Paneer and Palak Paneer.
- Rice, daal and sabji are **bowls** and get Small / Medium / Large (×0.6, ×1.0, ×1.5).
  Rotis and eggs are **pieces** and just get a count.
- **750 foods.** 226 from USDA FoodData Central (`FoodSeed.kt`) plus 524 Indian dishes and meal
  combos/thalis from the Indian Food Nutrition Database workbook (`IndianFoodSeed.kt`, generated by
  `tools/foodseed/indian_db.py`; `Catalogue.kt` joins the two). Same format for both; workbook dishes
  already in the USDA list were skipped, and their vitamins come from the linked INDB recipe or are 0.
- **The original numbers come from USDA FoodData Central, not from guesswork.** 226 foods across
  fourteen categories — North and South Indian, chaat and street food, Italian, fast food —
  each carrying calories, protein, fibre, vitamin A, vitamin C, iron and calcium for one
  medium serving. `FoodSeed.kt` is *generated*; see [tools/foodseed](tools/foodseed/) for the
  sources, the method, and a per-food audit trail. Add your own item with exact numbers and it
  joins the same searchable list permanently.
- A single item at or above `Settings.itemWarnKcal` (default 300) is flagged red, and any meal
  past its own budget goes red too.
- **The ring shows what you have eaten, not what is left.** Intake is the number being tracked;
  the headroom is derived from it, so it sits underneath in small type ("760 left", or
  "240 over" once you pass the goal).
- **Every nutrient scales by portion together**, so a large (×1.5) bowl of daal is 327 kcal,
  19.4 g of protein and 16.8 g of fibre — one multiplication, applied to the whole panel, so
  fibre can never be summed in a place that forgot vitamin C. Goals are whole-day numbers
  (`Settings.proteinGoal`, `Settings.fiberGoal`) rather than four per-meal ones, but each meal
  card still totals its own grams.
- Protein and fibre read the opposite way round to calories: reaching the goal is the win, so
  their bars turn green on arrival instead of red, and there is no "over". Defaults are the
  ICMR-NIN adult recommendations — 60 g protein, 30 g fibre.
- **Vitamins and minerals are shown as a share of a day**, not in micrograms, because nobody
  reads 340 µg of vitamin A as anything. Vitamin A, vitamin C, iron and calcium, against the
  ICMR-NIN reference intakes in `DailyValue`. Iron is set to 19 mg rather than the Western 18:
  non-haem iron from plants is absorbed far less readily than the haem iron in meat.
- These are averages of real foods, not of *your* food — a home kitchen's daal is not a
  laboratory's. The point is a trend you can trust, not a clinical record.
- **Goals are calculated from your profile, automatically.** Fill in the Profile screen and the
  calorie goal comes from **Mifflin-St Jeor** (`BodyMath`), protein from body weight
  (1.0–1.6 g/kg by activity), fibre at 14 g per 1000 kcal, and the four meal budgets re-split
  25/35/10/30. Change your weight or activity level and every target moves with it — there is
  no button to press. Typing a goal by hand turns `autoGoals` off, so a number you chose is
  never overwritten by the next profile edit. The whole profile is optional; leave it blank and
  the app behaves exactly as it did before it existed.

### Habits
- Timed habits store **milliseconds**. The original build rounded a 3-second timer up to a
  whole minute; the stopwatch on screen and the number banked are now the same value.
- **Reset** restarts the running stopwatch at zero without leaving the habit. **Reset today**
  wipes what has been banked today.
- The five starter habits are `seeded`: they **archive** rather than delete, so history is
  never orphaned and the tab can never end up empty. Habits you add yourself delete outright.

### Daily routine
Ten fixed items seeded from `Routine.SEED` - wake-up 7:00 and meditation/gym 7:30 (alarms),
breakfast 9:30, lunch 1:30, walk 2:00 (notifications), evening activity 7:00 PM (alarm),
learning 8:00, dinner 9:00, reading 9:45 and "plan tomorrow" at 10:00 (notifications).
- **Usual times** live on `routine_items` and are edited in Alarms → Daily routine.
- **Tomorrow's plan** (`routine_plans`, one row per item per day) moves or switches off a single
  day. The 10 PM notification opens it; saving it is what ticks "Plan tomorrow".
- **Hit or miss** (`routine_logs`): Done / Skip on the notification, or ✓ / ✗ in the Routine tab.
  Some items tick themselves: holding to dismiss the wake-up alarm, a meal logged in that slot,
  1,000 steps in the two hours after the walk, a saved plan. Untouched items turn into misses
  three hours after their time (one hour for wake-up). Days before `RoutineStart` don't count.
- Scheduling is `RoutineScheduler`, sharing `AlarmReceiver`/`AlarmService` with reminders but in
  its own request-code band (ring ids from 3,000,000).

### Alarms
Three or four separate Android permissions decide whether a reminder ever reaches you, each in
a different Settings screen. The Alarms tab shows all of them with a fix button next to each,
plus a "send a test in 10s" button so the chain can be proven rather than assumed.

- `POST_NOTIFICATIONS` — Android 13+.
- `SCHEDULE_EXACT_ALARM` — **denied by default on Android 13+**. `USE_EXACT_ALARM` is also
  declared, which is granted at install and is what actually makes alarms land on the minute.
- Battery optimisation exemption — some OEMs drop alarms without it.
- `USE_FULL_SCREEN_INTENT` — Android 14+. Without it an alarm degrades to a heads-up
  notification instead of taking over the lock screen.

Alarms go out via `setAlarmClock()`, the one alarm type Doze and App Standby are not allowed to
defer. In ALARM mode a foreground service plays the alarm ringtone and vibrates for
`ringSeconds` (default 20) while a full-screen activity offers Snooze and Dismiss.

### Activity
**Steps update in the background.** `StepSyncJob` (plain `JobScheduler`, every 15 minutes,
survives reboot) calls `StepRecorder`, which re-reads the last two days from Health Connect, or
samples the phone's step counter when Health Connect isn't connected. Health Connect only answers
a closed app once **background access** is granted - the Activity tab asks for it. Each refresh
also re-reads the last 7 days' totals, so a day synced at lunchtime doesn't keep its lunchtime number.

**Steps by the hour** (`hourly_steps`) drive the "When you walked" chart. The step counter's
readings are spread over the hours between readings (`StepSplit`); its last reading is kept in
its own preferences file, not the settings row.

Health Connect is read-only and de-duplicated, so a phone and a watch are not double-counted.
On first connect the app **backfills up to six months** of history into `daily_metrics`, so the
charts are useful immediately. If Health Connect is unavailable, steps fall back to the phone's
`TYPE_STEP_COUNTER` sensor. Failures are shown in plain words — an earlier build swallowed
every exception, so a permission problem looked identical to "0 steps".

### Screen time
**Limits are enforced** with Usage access plus *Display over other apps* (Settings → Limit
blocking) - no accessibility service, so nothing on screen is ever read. `LimitWatchService` is
a foreground service (quiet, minimum-priority notification) that runs only while at least one
limit is set and both accesses are on. Every 2 s while the screen is on it reads the newest
usage events to see which app is in front; a tracked app past its limit is sent to the home
screen with a toast and `LimitReachedActivity`. Blocking can lag a couple of seconds. It is
started from app start, on resume, on boot, by the 15-minute job and whenever limits change.
Without the overlay access a limit only colours the bar.

Foreground time comes from `UsageStatsManager`'s event stream (RESUMED/PAUSED pairs) rather
than `queryUsageStats`, which is bucketed and over-counts. Chrome is counted as a whole; Android
cannot see which sites you visit inside it. The five starter apps cannot be removed; apps you
add yourself can.

## Data retention

**Everything is kept for 180 days (six months), then pruned on the next launch.**

One knob, in `data/Retention.kt`:

```kotlin
object Retention {
    const val DAYS: Long = 180
}
```

`Repository.prune()` runs from `LifeTrackApp.onCreate` on a background thread and deletes rows
older than the cutoff from `meals`, `sessions`, `habit_checks`, `app_usage_days`,
`daily_metrics`, `step_days`, `hourly_steps`, `routine_plans` and `routine_logs`. The food catalogue, habits, tracked apps, reminders and
settings are never pruned — only the day-by-day rows.

**Tuning it:**

| Want | Do |
| --- | --- |
| Keep a year | `DAYS = 365` |
| Keep everything | `DAYS = 36_500` (a century — simpler than special-casing "never") |
| Keep less | Lower it, but see the warning below |

A day of tracking is a few kilobytes, so six months of everything is comfortably under a
megabyte. The limit exists to stop the database and the charts growing without end, not to save
space — raise it freely.

⚠️ **Raising `DAYS` does not bring back what has already been pruned.** Raise it *before* you
need the history, not after. If you are unsure, raise it now.

The 6-month window is also what the "6 months" option in every detail screen charts, and what
`HealthSync.importHistory()` backfills by default.

`tools/foodseed/` sits outside the app and never ships in the APK: it is the Python that turns
USDA FoodData Central into `FoodSeed.kt`, plus `mapping_audit.txt`, which names the exact
database entry behind every number in the catalogue.

## Shared UI pieces worth knowing

- **`WeekStrip`** — seven small rings, one per day, each filled to that day's share of the goal,
  with today outlined. A week of history in the height of one row. The trend charts answer "how
  much"; this answers "did I, on each of the last seven days". On Home it tracks steps.
- **`PeriodPicker`** — the dropdown on every detail screen: Today / This week / This month /
  3 months / 6 months. It replaced a three-way pill switcher, which stops being readable past
  about four options. Six months is the last stop because `Retention` prunes past it — offering
  "this year" would show half a year of blank.
- **`HistoryList`** — one row per day, newest first, with the day's numbers written out. A chart
  shows the shape of a window; this answers "what did I actually eat on the 14th".
- **`ChartDetailSheet`** — **every chart in the app is tappable.** Tap a bar, a point on a line,
  a donut slice or a breakdown row and a bottom sheet opens with the value, how it sat against
  the goal, how it compared to your average, where it ranked, and how it moved against the day
  before. Charts are good at shape and bad at specifics; rather than cram numbers onto them,
  each hands the tapped element to one shared sheet. `dayDetail` builds the answer for a day,
  `sliceDetail` for a slice, so a bar and a donut answer the same questions in the same order.
  A line chart has no bars to hit, so the whole canvas is the target and the x position picks
  the nearest day — at six months the points are a couple of pixels apart, and demanding a
  precise hit would make the long windows untappable.

## Design system

- **Type**: Outfit (headings and numbers), Plus Jakarta Sans (body), JetBrains Mono (the
  stopwatch — a proportional font makes the digits jitter). All three are Google Fonts bundled
  as variable TTFs in `res/font`, so they render correctly offline and without Play Services.
- **Colour is state, never decoration.** Green means on track or under budget, red means over
  or behind, amber means close. Always via `accents()` — never a raw hex value in a screen.
- Each section keeps its own accent so the tabs read as different places.
- **Spacing** comes from `Space` (4dp steps) and **elevation** from `Elevation` (three levels
  only), so screens written at different times still line up.

## Tests

```bash
JAVA_HOME=~/.jdks/jbr-21.0.11 ./gradlew :app:testDebugUnitTest
```

The migration tests are the ones that matter most: they replay the real upgrade SQL against a
real SQLite file and assert the resulting column lists match what Room generates. A mismatch
there is not a failing test, it is a crash on launch for anyone who already has data.

## Database versions

| Version | Change |
| --- | --- |
| v3 | Meals, activities, sessions in **minutes**, reminders, tracked apps, step days |
| v4 | Sessions in **seconds**; meals gain slot/quantity/portion; food catalogue added |
| v5 | Activities become **habits** (timed or counted); sessions in **milliseconds**; habit checks; alarm fields on reminders; per-meal budgets; `app_usage_days` and `daily_metrics` history |
| v6 | **Protein**: grams on `food_items` and `meals`, a daily goal on `settings` |
| v7 | **Fibre, vitamin A, vitamin C, iron, calcium** on both tables; `protein` widens to REAL; `settings` gains a fibre goal and `seedVersion` |
| v8 | **Body profile** on `settings`: height, weight, age, sex, activity level — all optional |
| v9 | `autoGoals` — the switch that keeps the calorie, protein and fibre goals in step with the profile |
| v10 | Daily routine (`routine_items`, `routine_plans`, `routine_logs`) and `hourly_steps` — new tables only |

`fallbackToDestructiveMigration()` is still set as a last resort for anyone on a build older
than v3. Every upgrade from v3 onwards preserves data.

v6 is three plain `ALTER TABLE ... ADD COLUMN` statements. v7 has to **rebuild** `meals` and
`food_items` instead, because widening `protein` from INTEGER to REAL is not something SQLite
can do in place — a roti really is 4.5 g, not 4 or 5. Every row is copied across; `MigrationTest`
replays the whole v3 → v4 → v5 → v6 → v7 chain against a real SQLite file and asserts the
resulting column lists, because a mismatch there is not a failing test, it is a crash on launch
for anyone who already has data.

**Meals keep the numbers they were logged with.** Correcting a catalogue figure — or the whole
catalogue moving to measured USDA data, as it did in v7 — never silently rewrites what you ate
last month. Rows logged before a nutrient existed carry 0 for it, which is the only honest
answer: nobody can know what was in them.

**The catalogue itself does refresh.** Seeding only runs on an empty table, so
`Repository.ensureSeeded` compares `Settings.seedVersion` against `FoodSeed.VERSION` and
re-points the seeded foods at the current figures when it is behind, adding any new ones.
Foods you created yourself (`custom = 1`) are never touched, even if one shares a name with a
catalogue entry.
